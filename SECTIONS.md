# SECTIONS.md — секции, дизайны и проекты на одном сервере

**Дано, а не замысел.** Документ описывает архитектуру, по которой один сервер несёт несколько
проектов, каждый в своём дизайне, и по которой пользователь может привести свой дизайн и переписать
в нём весь проект, не потеряв ни строчки содержимого. Часть описанного здесь уже построена, часть —
нет; раздел §9 честно разделяет одно и другое, и ни один раздел не выдаёт план за факт.

Смежные документы: `CONTENT-ENGINE.md` (как устроен материал), `CODING-STANDARDS.md` (лимиты),
`DESIGN.md` (токены темы).

---

## 1. Задача, из которой всё следует

Пользователь разворачивает сервер и получает не один сайт, а **место, где живут несколько проектов**.
Главная — рубрикатор; за маршрутами — разные продукты: сервис записи, доска объявлений, аренда, клон
чего угодно. Завтра он говорит: «ваш дизайн мне не нравится» — берёт навык, создаёт свою идентичность и
**переписывает проект в ней, оставаясь на наших паттернах**. Соседний проект при этом продолжает жить в
своём дизайне, и ни одна страница не смешивает два.

Из этой задачи следуют три требования, и всё остальное в документе — только их исполнение:

1. **Содержимое переживает смену дизайна.** Иначе «перепишите мне всё в моём стиле» означает переписать
   и все статьи, а это не смена дизайна, а новый сайт.
2. **Дизайны не текут друг в друга.** Ни цветом, ни шрифтом, ни классом.
3. **Дизайну есть куда лечь.** Не «поправьте наши компоненты», а своя папка, свой манифест, своё место.

---

## 2. Три уровня, которые нельзя путать

| Уровень | Что это | Чей | Меняется под дизайн |
|---|---|---|---|
| **Контракт данных** | `quote` = текст + автор; `table` = заголовки + строки | платформы, один на всё | **никогда** |
| **Набор секций** | КАК рисуется `quote` | дизайна, свой у каждого | это и есть дизайн |
| **Страница** | последовательность блоков | проекта | не знает имени дизайна |

**Почему контракт один.** Материал написан один раз и должен рисоваться любым дизайном. Разреши дизайну
менять форму данных — и статья, написанная под дизайном A, перестанет существовать под B. Тогда обещание
«ваш контент останется вашим» превращается в ложь ровно в тот день, когда пользователь решит им
воспользоваться.

**Что делать, если дизайну нужна возможность, которой в контракте нет.** Не расширять свои данные, а
**добавить вид в общий каталог** — он появляется у всех дизайнов сразу, и у каждого встаёт честный
вопрос: рисую я его или объявляю непокрытым (§5). Дизайн, у которого «свои поля», — это форк продукта,
а не дизайн.

## 3. Проект = маршрутная группа

**Единица, к которой привязан дизайн, — проект, а не страница и не сайт.**

```
app/[lang]/
  page.tsx                 рубрикатор: перечисляет проекты сервера
  (booking)/               ПРОЕКТ: сервис записи
    _data/project.ts       манифест: дизайн, роли, языки, данные
    …его страницы
  (rentals)/               ПРОЕКТ: аренда, другой дизайн
    _data/project.ts
    …его страницы
```

**Манифест проекта** (`_data/project.ts`) — единственное место, где написано имя дизайна:

```ts
export const project = {
  slug: 'booking',
  design: 'midnight',        // папка в sections/
  roles: 'public',           // кому видны публичные страницы проекта
}
```

**Почему не страница выбирает дизайн.** Выбор, сделанный на странице, размазывается по десяткам файлов, и
первая же новая страница, забывшая его повторить, нарисуется чужим набором. Ошибка при этом не падает —
страница просто выглядит не так, а увидит это человек и не сразу. Одна запись на проект делает смешение
невозможным по построению, а не по внимательности.

**Почему не отдельное приложение на порт.** Это тоже развело бы дизайны — ценой отдельной сборки,
отдельного процесса и отдельной авторизации у каждого проекта. Маршрутная группа даёт ту же изоляцию
внутри одной сборки, сохраняя общими то, что и должно быть общим: слой данных, авторизацию, панель.

## 4. Дизайн = папка с рендерерами, манифестом и токенами

```
sections/
  contract.ts              что обязан объявить любой дизайн
  fractera/                дизайн по умолчанию — наш
    manifest.ts            какие виды покрыты
    theme.css              токены: цвета, шрифт, радиусы
    blocks/quote.server.tsx      ОДИН вид — ОДИН файл
    blocks/table.server.tsx
    …
    cards/post-card.server.tsx   карточки списков — тоже секции
  midnight/                дизайн пользователя, созданный навыком
    manifest.ts
    theme.css
    blocks/…               только то, что он переписал
```

**Файл на вид — не вкусовщина, а исполнение лимита.** Правило проекта: функциональный компонент не длиннее
200 строк (данные и типы не в счёт). Сегодня все шестнадцать рендереров слиплись в один реестр на 263
строки кода — то есть эталон нарушает собственное правило именно там, где его труднее всего заметить.
В раскладке «один вид — один файл» каждый рендерер занимает 10–40 строк, и лимит перестаёт быть
требованием, которое надо помнить: он становится следствием того, как лежит код.

**Токены живут на корне проекта, а не на корне документа.** Обёртка проекта объявляет свой набор
CSS-переменных на своём корневом элементе; рендереры по-прежнему пишут `bg-background`, `text-foreground`,
а какое это значение — решает проект. Отсюда два следствия: два дизайна на одном сервере не перекрашивают
друг друга, и светлая/тёмная тема продолжает работать внутри каждого. Абсолютный цвет (`bg-black`,
`text-white`, именованный акцент) внутри папки дизайна запрещён — это тот самый дефект, из-за которого
блог оставался чёрным под светлой темой, и в чужом дизайне он вернётся первым.

## 5. Манифест покрытия: расхождение — задача, а не отказ

Дизайн **не обязан** повторять состав соседа. У одного есть карточка с картинкой, у другого нет; у одного
шестнадцать видов, у другого шесть. Это нормальное состояние, и оно должно быть **видимым**.

```ts
export const manifest = {
  design: 'midnight',
  covers: ['p', 'h2', 'h3', 'quote', 'figure', 'cta'],
  inherits: false,          // молчаливого наследования от дефолта нет
}
```

`npm run read:sections` печатает три списка по проекту:

- **покрыто** — вид есть в дизайне и встречается в содержимом;
- **не покрыто** — вид есть в содержимом, а в дизайне его нет: **это задача** — либо дописать секцию,
  либо переписать содержимое под то, что дизайн умеет;
- **лишнее** — дизайн умеет то, чего в содержимом нет: подсказка, а не ошибка.

**Почему не наследовать молча.** Тихий фолбэк на наш дефолт даёт страницу в двух почерках и создаёт
впечатление законченного дизайна там, где он наполовину не написан. Наследование допустимо только явно —
строкой `inherits: true` в манифесте, и тогда витрина помечает унаследованные виды, чтобы смешение
почерков осталось фактом, а не сюрпризом.

## 6. Витрина: дизайн видно целиком, а не по кусочкам

Вкладка **Секции** в слое прав архитектора: подвкладка на дизайн, внутри — все его виды, нарисованные
настоящими рендерерами на образцовых данных. Не индексируется, машинной версии не имеет, образцы не
переводятся: это инструмент того, кто строит, а не материал для посетителя.

Витрина отвечает на три вопроса, ради которых и существует: **что у нас есть** (агент читает её вместо
чтения кода), **как это выглядит вживую** (владелец смотрит глазами) и **что дизайн покрыл, а что взял у
дефолта**.

🔒 **Витрина рисует блоки общим рендерером и не имеет собственной вёрстки блоков.** Витрина со своей
разметкой показывает себя, а не продукт: дефект вроде «текст цвета страницы на цветной заливке» останется
на ней невидимым — именно так он и прожил в кнопке `docref`, которую не рисовал никто.

## 7. Что принадлежит платформе навсегда

Дизайну не принадлежит и меняться под него не может:

- каталог видов и их поля;
- резолвер языков и языковые ячейки;
- генератор списков (`parser-fs`), карты сайта, `llms.txt`, markdown-двойники;
- маршрутизация, авторизация, слой данных;
- гейты.

Дизайн, дотянувшийся до этого списка, перестаёт быть дизайном: это форк продукта, который дальше
поддерживает тот, кто его сделал.

---

## 8. Четыре запрета

1. **Два дизайна на одной странице.** Смешение — не гибкость, а неотличимость поломки от замысла.
2. **Дизайн, добавляющий поля в данные.** Контент перестаёт быть переносимым — см. §2.
3. **Контент, называющий имя дизайна.** Статья, знающая, что она «в midnight», не переедет никуда.
4. **Абсолютный цвет внутри папки дизайна.** Только токены — иначе тема ломается ровно наполовину.

## 9. Что есть сегодня, а чего нет

**Есть:** контракт данных (`lib/content/blocks/types.ts`, 16 видов, ноль импортов); один набор рендереров;
витрина (`app/[lang]/(protectedLayer)/(admin)/blocks`), где все виды нарисованы; гейт `check:blocks`
(у каждого вида есть образец; сплошная заливка несёт парный цвет).

**Нет:** понятия «проект» (сегодня сервер несёт один сайт); привязки дизайна; папки `sections/`; второго
набора; манифеста покрытия; `read:sections`; токенов на корне проекта — тема сегодня одна, глобальная;
карточек списков как секций (они инлайном внутри блога, поэтому «дизайн блога» пока перекрашивает статьи
и не трогает список).

**Отсюда порядок работ:** сначала секции становятся слоем (иначе главную и каталог пришлось бы
переписывать дважды — сперва в блоки, потом в дизайны), и только затем на этот словарь переводятся
главная, публичный каталог и приватные маршруты.

## 10. Проверки

| Команда | Что отвергает |
|---|---|
| `npm run check:sections` | вид каталога без образца; сплошная заливка с текстом цвета страницы; абсолютный цвет в папке дизайна; манифест, объявляющий вид, которого нет |
| `npm run read:sections` | ничего не отвергает — печатает покрытие проекта: покрыто / не покрыто / лишнее |
| `npm run check:types` | рендерер, не соответствующий контракту вида |

**Почему проверкой, а не соглашением.** Соглашение живёт, пока о нём помнят; первый же дизайн, привезённый
навыком в пятницу, проверит это на прочность. Гейт держит границу без участия памяти.
