# koleso-balansa — дерево замысла на архитектуре Fractera

**Первый артефакт режима `migration`** (закон 3: дерево раньше таблицы возможностей и раньше первого
шага). Источник — `https://github.com/bolshiyanov/kolesoBalansa`, прочитан 2026-08-22.
Пробный разбор: дерево построено, код НЕ переносился.

## Что это за продукт (прочитано из кода, не спрошено у владельца)

«Колесо баланса» — трекер личного развития с двумя ролями. **Клиент** ведёт сферы жизни (`Area`),
оценивает их сегменты замерами (`Segments` → `CompletedSegments`) и держит привычки
(`Activities` → `Frequency` → `CompletedDays`). **Коуч** видит своих клиентов, раздаёт шаблоны и
приглашения. Сверху — подписка с пробным периодом и три экрана статистики: колесо баланса, пульс дня,
активности.

## Их стек → наш контур

| В оригинале | На Fractera | Почему так |
|---|---|---|
| Next 14, app router | Next 16 стартера | тот же фреймворк, переносится напрямую |
| Prisma + PostgreSQL (внешняя база) | `SCHEMA` в `lib/db/index.ts`, слой данных :3300 | таблица заводится одной константой и появляется в обеих средах; отдельных миграций нет |
| Clerk (`clerkUserId` в каждой таблице) | слой авторизации Fractera :3001, 82 языка | своя дверь входа, ролевая модель панели; чужой `clerkUserId` становится нашим `user_id` |
| UploadThing (`Images`) | медиа-слой панели | хранилище уже стоит на сервере владельца и входит в те же три евро |
| MUI + Radix + Emotion + Tailwind | shadcn + примитивы стартера | закон 0: папка импортит `@/components/ui/*`; четыре библиотеки UI в одном проекте — источник расхождений |
| ApexCharts + Recharts | один графический примитив стартера | две библиотеки графиков делают одну работу дважды |
| 12 React-контекстов | серверные компоненты + островки | контекст владеет маршрутом, а маршрут обязан остаться статическим |
| Vercel Analytics | телеметрия сервера | внешний счётчик не нужен: сервер свой |

🔒 **Файлы не переносятся.** Их код прочитан как ОПИСАНИЕ возможностей; здесь строится тот же смысл на
нашей архитектуре. Из оригинала едут: модель данных, состав экранов и правила ролей.

## Таблицы (в `SCHEMA`, префикс продукта)

| Таблица | Из чего | Заметка |
|---|---|---|
| `p1_areas` | `Area` | `clerkUserId` → `user_id` нашей авторизации |
| `p1_segments` | `Segments` | уведомления — через каналы платформы, не своим полем времени |
| `p1_segment_marks` | `CompletedSegments` | замер: дата, значение, комментарий |
| `p1_activities` | `Activities` | привычка внутри сферы |
| `p1_activity_schedule` | `Frequency` | тип, дни, число раз |
| `p1_activity_marks` | `CompletedDays` | отметка дня |
| `p1_coach_clients` | `Students` | связь коуч ↔ клиент со статусом запроса |
| `p1_invites` | `Invite` | приглашение по коду |

**Чего в таблицах НЕ будет.** `User` целиком: имя, почта, аватар, роль живут в слое авторизации
платформы — дублировать их в продукте значит завести второе место правды о человеке. Поля подписки
(`typeSubscription`, `statusSubscription`, даты, `trialPeriod`) переезжают в `p1_subscriptions`
отдельной строкой на пользователя. `Images` не переезжает вовсе — файлы живут в медиа-слое.
