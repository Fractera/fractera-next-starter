# 533 — режим `migration`: перенос существующего проекта на Fractera

**Заведён 2026-08-21.** Владелец назвал это критической проблемой дня и решил начинать с него.

## Почему это критично, а не «ещё одна возможность»

**Обещание уже опубликовано, а механизма нет.** На главной странице стоит раздел «Как перенести ваш
проект на Fractera» — семь шагов, от покупки сервера до переноса данных. Он описывает работу как
действующую; это решение владельца, страница выпущена под запуск.

Физически нет ничего: вкладки «Переезд на Fractera» в панели, значения `migration` в
`PLATFORM-CONFIG.developmentMode` (тип его знает, но панель не предлагает), разбора чужого
репозитория, порождения шагов из декомпозиции, переноса данных. Навыка `use-migration` тоже нет.

🔒 **В публичных текстах об этом ни слова** — прямой запрет владельца. Никаких «скоро», «в
разработке», «пока недоступно». Памятка живёт в инструкции агента и дальше неё не идёт.

## Что это за режим по существу

Четвёртый режим разработки рядом с `classic`, `steps`, `cases`. Отличие от `cases` — в источнике
очереди шагов: там она рождается из подтверждённых кейсов, здесь **из кода, который уже существует**.
Кейс отвечает «что должно быть», разбор — «что уже есть».

Порядок, объявленный владельцем:

1. агент читает чужой проект: архитектура, зависимости, что от чего зависит;
2. из прочитанного рождается **декомпозиция**, а из неё очередь нумерованных шагов;
3. первым срезом встаёт **каркас**: адреса, таблицы, вход, публичный и закрытый репозитории — здесь
   же владельца спрашивают о правах доступа к возможностям;
4. дальше возможности добавляются по одной, шаг за шагом, с доказательством на каждом;
5. последними переносятся **данные** — по доступу, который владелец даёт сам.

## Подшаги (предложение, уточняется с владельцем перед стартом)

| № | Что | Почему отдельно |
|---|---|---|
| 533-1 | включение режима: значение в `PLATFORM-CONFIG`, вкладка в панели, чтение агентом | без этого остальное некуда включить |
| 533-2 | чтение чужого репозитория: откуда берётся адрес, что именно читаем, куда кладём прочитанное | самая объёмная часть; здесь же граница «читаем, но не исполняем чужой код» |
| 533-3 | декомпозиция → очередь шагов в `new-steps/` | ложится на уже существующую память проекта |
| 533-4 | каркас первым срезом: адреса, таблицы, вход | точка, после которой владелец видит свой проект живым |
| 533-5 | навык `use-migration` — пишется ИЗ постройки, а не до неё | тот же порядок, что дал `use-dynamic-pages` |
| 533-6 | перенос данных | последним и по отдельному доступу: до этого момента ошибка стоит дёшево |

## Вопросы, на которые нужен ответ владельца до старта

1. **Откуда берётся чужой проект** — адрес репозитория, архив, доступ к работающему серверу?
2. **Что делать с несовместимым** — чужой стек не Next, чужая база не SQLite: отказ, частичный
   перенос или разговор?
3. **Кто решает, что «перенесено»** — сравнение возможностей списком, или его слово?

## Чего в этом шаге НЕ делаем

- Не пишем `use-migration` до постройки: навык, написанный до, описывает замысел, а не то, обо что
  споткнулись.
- Не трогаем публичные тексты (запрет выше).
- Не переносим данные раньше каркаса: данные последними — это порядок владельца, и он снижает цену
  ошибки на каждом предыдущем шаге.

## Ответы владельца, полученные 2026-08-22 (два из трёх)

**Несовместимый стек — не отказ и не переписывание.** Дословно: «not need replace code, it work as use
case, but with code examples, not need quiz, but need full planning after original code research».
Читается так: чужой код — это ОПИСАНИЕ возможностей, из него рождается кейс, и кейс несёт примеры кода
оригинала. Опроса продукта нет: ответы уже написаны в коде, спрашивать их второй раз значит просить
работу, которую владелец однажды сделал. Планирование — полное и ПОСЛЕ исследования оригинала, а не по
шагу вслепую.

**Приёмка — дерево первым, слово последним.** Дословно: «first need create fs tree with original idea
using Fractera architect, after Таблица возможностей + ваше слово». Первым артефактом строится дерево
файлов замысла оригинала по архитектуре Fractera; дальше агент ведёт таблицу возможностей и закрывает
каждую доказательством; перенос объявляет состоявшимся владелец.

**Без ответа остался первый вопрос — откуда берётся чужой проект** (адрес репозитория, архив, доступ к

## 533-6 — перенос данных и ключей облачных сервисов (требование владельца 2026-08-22)

**Последний кусок работы — переподключить то, что в старом проекте уже работает:** базы данных,
хранилища файлов, почту — если старый поток жив. Исходная посылка: в старом потоке владелец почти
наверняка сидел на облачных сервисах, и у каждого есть ключ.

**Порядок, названный владельцем:**

1. Агент даёт ссылку на страницу панели «Переменные окружения» (`/<lang>/env`) — там владелец заводит
   СВОИ ключи и значения: база, хранилище, почта, что угодно ещё.
2. Дальше он повторяет **перенос переменных на локальную машину** — той же кнопкой «копировать →
   вставить», которой пользовался при первой настройке, чтобы клон на его машине видел те же значения.
3. 🔒 **Развилка, которую агент обязан предложить, а не решить за него:** ключи можно вообще не хранить
   на сервере и держать только на локальной машине. Тогда шагов меньше — владелец ставит ключи у себя,
   говорит «ключи добавлены», и всё. Выбор его: сервер удобнее, локально — теснее к секретам.

**Строить для этого нечего — механизм существует.** Страница `env` панели уже умеет и правку значений
(секреты отдаются маской, не открытым текстом), и перенос файла на машину с отметкой о переносе
(`ENV_TRANSFERRED_KEY`). Задача 533-6 — не новая поверхность, а порядок в навыке `use-migration`.

🔒 **Навык пишем СВОЙ, чужой не берём в чистом виде** (владелец 2026-08-22). У нас своя архитектура;
`persist-env-var-with-rebuild` — опора и источник идей (сборочная переменная живёт только до пересборки,
писать через настоящий сеттер, а не руками), но `use-migration` ссылается на него, а не повторяет его.

## 533-3 СДЕЛАН 2026-08-22 — очередь шагов рождается из дерева

**Механизм записан в инструкцию агента** (`CLAUDE.md`, режим `migration`), шесть правил порождения:
кейсы раньше шагов и с кодом оригинала · каркас первым и один · одна возможность — один шаг · у каждого
шага назван кейс и доказательство · данные последними по отдельному доступу · **дефекты оригинала
называются в шаге, а не переносятся молча**.

**Где лежит очередь.** У владельца — обычная очередь проекта (`new-steps/`), потому что переезд и есть
его разработка. В нашей мастерской пробный разбор чужого проекта живёт под своим деревом.

### Проверено на живом проекте владельца

`https://github.com/bolshiyanov/kolesoBalansa`, 287 файлов. Порождено:

- **5 кейсов** — `MIGRATION/koleso-balansa/USE-CASES/`, каждый с фрагментом оригинала, из которого
  прочитан. Опроса не было ни одного вопроса: ответы взяты из кода, как и требует закон 2.
- **13 шагов** — `MIGRATION/koleso-balansa/STEPS/`, от каркаса до переноса данных, с зависимостями.

### Четыре дефекта оригинала, которые нельзя переносить (найдены чтением, не догадкой)

| Что | Где | Чем грозит |
|---|---|---|
| личность из ТЕЛА запроса (`clerkUserId` в JSON) | все маршруты `app/api/*` | подставил чужой идентификатор — получил чужие данные |
| личность из АДРЕСА в `localStorage` | `app/page.tsx` + `api/invite-generate` | вход под чужим именем без пароля вовсе |
| правило доступа коуча переписано в каждом маршруте и проверяет не то | `api/segments`, `api/students` | коуч видит не своих клиентов |
| длина пробного периода константой в двух файлах | `api/user/fetch-coach`, `fetch-student` | правится в одном — расходится молча |

Ещё три вещи попроще: даты строками (`date String`), две библиотеки графиков разом, поля напоминаний
без рассылки.

**Что это доказывает про режим.** Разбор чужого кода даёт не только «что переносить», но и «что чинить
по дороге» — и это его главная ценность против пересборки с нуля.
